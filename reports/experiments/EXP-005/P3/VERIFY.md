## 1. blocked 사유 재현

- `python -m algaecast.collect.kma_apihub_fcst --out <임시>/probe_verify.json`을 다시 실행했다(약 10초). 저장소의 `probe.json`은 덮어쓰지 않았다.
  - 핵심 경로 `nph-dfs_shrt_grd`를 포함한 단기예보 자료 API 8개가 모두 HTTP 403 "활용신청이 필요한 API 입니다. 활용신청 후 다시 시도해 주십시오."를 돌려줬다.
  - 예보구역 조회 2개는 200이다.
  - 핵심 경로에 가짜 키를 넣으면 401 "유효한 인증키가 아닙니다."가 나온다.
  - 공공데이터포털 단기예보 2.0은 HTTP 200에 resultCode=10 "최근 3일 간의 자료만 제공합니다."를 돌려준다.
- 판정 dict(`key_valid` true, `data_access` false, `alt_access` [])가 원본과 같다. `metrics.json`의 probe 목록도 `probe.json`의 (이름, HTTP)와 같다.
- 따라서 "키는 유효하고, 자료 API는 활용신청을 하지 않았다"는 해석이 응답 코드 구조(401·403·404 구분)와 맞는다. 현재 키로 과거 단기예보를 받을 수 있는 대체 경로는 이번 점검에서 확인되지 않았다.
- `data/raw/kma_fcst_hist/`는 없다. `data/raw/cache/`에서 12:00 이후 생긴 파일 28개는 모두 wamis 응답이다(P6 작업으로 보임). API허브·단기예보 흔적은 0개다. 같은 시간대 `collect_errors.log` 3줄도 wamis_dam 줄이다. P3 점검은 캐시를 남기지 않는다는 주장과 맞는다.

## 2. 2026 차단

- 코드 경로
  - `build_features` 진입 시 `H.guard_no_2026(df)`를 거친다. 기준일 2026-01-02 행은 RuntimeError로 거부되는 것을 확인했다.
  - `load_raw`는 `issued_at ≤ 2025-12-31 23:59`만 남긴다. 합성 parquet(2025-12-31 05:00, 23:00, 2026-01-01 05:00 발표)을 넣으면 앞의 두 개만 남는다.
- 산출물에는 평가 프레임·OOF·지표가 없다(`evaluation: null`). 따라서 "2025 지표가 목표일 ≤ 2025-12-31 행만인지"는 해당 사항이 없다. 참고로 `load_base`에는 목표일이 2026인 4행이 있다. 재개해서 평가할 때는 `harness2.metric_row2`(scope_masks)가 이 행들을 빼므로 현재 구조로 충분하다.
- 2026 시점 외부 호출: 실행자는 탐색 단계에서 2026-10-21 발표 **예보**를 1회 열람했다고 스스로 밝혔다(응답 앞 400자, 저장·지표 사용 없음). 2026 관측이나 정답이 아니고, 운영 수집(MT-05)과 같은 종류의 자료다. 그래서 PREREG의 "2026 계산 금지" 위반으로 보지 않았다. 다만 기록상 남겨 둔다(8절 minor).

## 4. as_of 누수(점검 3)

**코드.** `forecast_features`는 다음 순서로 자른다.
1. `cut_as_of(..., date_col="issued_at")`로 기준일 다음 날 이후 발표분을 버린다.
2. `issued_at ≤ 기준일 05:00`이고 `≥ 05:00 − 24h`인 발표분만 남긴다.
3. 그중 가장 늦은 발표 1개만 쓴다.

발효시각(fcst_at)은 기준일 +1~+3일이다. 이는 기준일에 이미 발표된 예보값이므로 '기준일 이후 관측' 금지에 걸리지 않는다. `as_of`에 시각(12:00)이 붙어도 결과는 같다(`issue_cutoff`가 normalize한다).

**실제 기준일 행으로 다시 계산.** P3 원자료가 없어서 실제 예보값으로는 검사할 수 없다. `data/raw/kma_forecast/`는 2026 자료라 열지 않았다. 대신 `harness.load_base()`에서 실제 (지점, 기준일) 40행을 뽑았다(2012-05-02~2025-09-01). 각 행의 기준일 −2~+2일에 하루 8회 합성 발표분을 붙였다. 결과는 다음과 같다.

| 시험 | 결과 |
|---|---|
| 전체 원자료로 `build_features` | 40/40 가용, 지연 0시간(05시 발표분 사용) |
| 행마다 cutoff 이후 발표분 삭제 후 `forecast_features` | 불일치 0칸 |
| cutoff 이후 값을 1e6으로 변조하고 05:00:01·05:30 발표분(−1e6) 추가 | 불일치 0칸 |
| 행마다 잘린 원자료로 `build_features`를 다시 계산(인덱스 보존 포함) | 완전히 같음 |

**테스트.** `pytest tests/test_exp_r2nd_p3_kmafcst.py`는 19개 모두 통과했다(3.96초). 이번 검증에서 전체 pytest는 돌리지 않았다. 후보가 없어서 PREREG (d) 판정 대상이 아니다.

## 8. 문제 목록

critical·major는 없다. 아래는 모두 minor다.

1. **수집 범위가 학습 구간보다 짧다.**
   - 가용률과 수집 계획(MANIFEST 조각 "2016-01~2025-12")은 기준일 2016~2025만 셌다.
   - 그런데 `load_base`는 2012-04-02부터이고, 2012~2015 학습 행이 194개 있다.
   - 재개할 때 이 행들을 수집할지 결측으로 둘지 정해야 한다. 모듈 설명에는 과거 자료가 2010-06부터라고 되어 있다.
2. **옛 연도 범주 이름은 확인되지 않았다.**
   - 2021년 단기예보 개편 전 동네예보는 기온 T3H(3시간), 강수 R06(6시간) 범주를 썼을 가능성이 있다.
   - 현재 함수는 TMP·PCP만 읽으므로, 그렇다면 옛 연도의 `ta_mean`·`rn_sum`(그리고 TMX가 없을 때 `ta_max`)이 결측이 된다.
   - 실행자가 적은 "+3일 결측 가능성"과 함께, 승인 뒤 응답 형식을 보고 확인해야 한다(검증자도 확인하지 못했다).
3. **늦은 발표분이 비어 있을 때 대체가 없다.**
   - 24시간 안에서 가장 늦은 발표분에 +1~+3일 값이 하나도 없으면, 더 이른 발표분으로 내려가지 않고 전체를 결측으로 처리한다.
   - 누수는 아니다. 다만 부분 결측 발표가 있으면 가용률이 낮아질 수 있다.
4. **탐색 단계에서 2026 예보를 열람했다.** 2026-10-21 발표 예보를 1회 봤다(4절 공개). 관측·정답·지표가 아니므로 규칙 위반으로 보지 않지만 기록해 둔다.
5. **소요 시간 표기가 다르다.** `metrics.json` 0.17시간, 실행자 보고 0.18시간, README "약 0.2시간"으로 조금씩 다르다. 결과에는 영향이 없다.
